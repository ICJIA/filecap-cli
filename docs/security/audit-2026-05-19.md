## Findings

### FC-2026-030 — Moderate — FIXED in 1.8.0-beta.3

**`references.graphqlEndpoint` and `references.restApiBase` lack URL-scheme validation, enabling SSRF / MITM via a malicious or accidentally-misconfigured `sites.json`.**

*Threat.* The Zod schema in `src/commands/web-rollup.js` (the source-of-truth for `sites.json`) accepts `graphqlEndpoint: z.string()` and `restApiBase: z.string()` with no further constraint. When `filecap references <siteName>` runs, both URLs are passed directly to `fetch()`:

```js
await fetcher(refsCfg.graphqlEndpoint, { method: "POST", … });
await fetcher(`${refsCfg.restApiBase}/api/posts?…`);
```

A `sites.json` handed to an auditor (the bundle-sharing workflow documented in the README) could therefore declare:

- `graphqlEndpoint: "http://localhost:8080/admin/api/graphql"` — SSRF to a local admin service.
- `restApiBase: "http://169.254.169.254/latest/meta-data"` — SSRF to the AWS instance-metadata endpoint on a cloud auditor's machine.
- `graphqlEndpoint: "http://strapi.example.com/graphql"` (no TLS) — passive MITM on any hostile network the auditor is on (coffee shop, conference WiFi).
- `graphqlEndpoint: "file:///etc/passwd"` or `"javascript:…"` — invalid for `fetch()` in Node but would fail with a confusing error instead of being rejected up-front.

The blast radius is bounded by two existing mitigations:
1. Extracted URLs are domain-filtered against the fleet whitelist before being written to a sidecar — so even a successful SSRF doesn't bulk-export internal data via the references pipeline.
2. Introspection queries are static (`{__schema{queryType{fields{name}}}}` and `{__type(name:"X"){fields{name type{name kind ofType{name kind}}}}}`) — no payload smuggling.

The actual harm is therefore mostly:
- **The unauthorized request itself.** POSTing a GraphQL query to an internal service can have side effects (think of webhook receivers or services that log on POST). The auditor's IP is the source.
- **Information leakage via timing / error responses.** A blind SSRF can enumerate local services or cloud-metadata fields by observing whether requests succeed or fail.
- **Passive MITM on http://** endpoints — same threat as fetching any http resource on a hostile network.

*Fix in beta.3.* The Zod refinement now validates that both URLs parse as `http:` or `https:` (via the `URL` constructor) and emits a soft warning when they're `http:` rather than `https:`. The fields are still strings (no semantic narrowing), but ill-formed values are rejected at load time:

```js
function parsedHttpUrl(label) {
  return z.string().refine((s) => {
    try { const u = new URL(s); return u.protocol === "http:" || u.protocol === "https:"; }
    catch { return false; }
  }, { message: `${label} must be an http(s) URL` });
}
// references: { graphqlEndpoint: parsedHttpUrl("graphqlEndpoint"), restApiBase: parsedHttpUrl("restApiBase"), … }
```

The SSRF protection against internal IPs (loopback / link-local / private ranges) is **not** added — operators sometimes do run internal Strapi instances and locking that down would break legitimate use. The trust boundary remains "you trust whoever handed you the sites.json bundle." The scheme check is defense-in-depth for the most common categories of mistake.

Three new tests cover:
- Bare `localhost:8080` rejected (no scheme).
- `file:///etc/passwd` rejected (wrong scheme).
- `javascript:alert(1)` rejected.
- `http://strapi.example.com/graphql` accepted (no error, optional warning depending on log-verbose).
- `https://…` accepted.

### FC-2026-031 — Low — FIXED in 1.8.0-beta.3

**`fetchAllEntries` paginators (v3 + v4) have no outer page-count cap.**

*Threat.* Both adapters loop until `data.length === 0` or `data.length < limit`. A site that returns a full page indefinitely (misconfigured, buggy, or hostile) would cause `filecap references` to allocate memory without bound — eventually OOMing the operator's process. Benign trigger: a Strapi install with a misconfigured pagination total. Hostile trigger: a poisoned sites.json points at a server that returns a steady 100-entry page on every request.

*Fix in beta.3.* Both adapters now accept `options.maxPages` with a default of 10,000. At `limit=100` that's a one-million-entry ceiling — well past any plausible real Strapi instance, but a hard guarantee that a runaway loop terminates. When the cap trips, the adapter throws so the orchestrator logs a WARN and moves on:

```js
let pages = 0;
while (true) {
  if (++pages > maxPages) {
    throw new Error(`fetchAllEntries: exceeded maxPages=${maxPages} for ${plural}`);
  }
  // …existing loop body…
}
```

### FC-2026-032 — Note — Accepted

**Sidecar NDJSON files consumed by `filecap cross-references` are trusted under the standard same-UID model.**

*Threat.* `runCrossReferences` reads every `--sidecar <path>` NDJSON file from disk, JSON-parses each line, and merges entries into the URL → referrers reverse index. If a malicious actor with same-UID access on the operator's machine can write to one of these sidecars, they can inject false references that appear on the final report. The reverse — deleting a sidecar — would silently drop coverage for that site.

*Status.* Same threat model as `~/.filecap/secrets.json` (FC-2026-020) and `~/.filecap/sites.json` itself — standard user-account trust. The sidecars are produced by `filecap references` runs the operator just executed; manipulating them would require write access to paths the operator just wrote to. Accepted as documented residual risk. If the trust model ever changes (e.g. sidecars become a sharable artifact like bundles), this should be re-evaluated.
