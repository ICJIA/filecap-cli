# ICJIA Fleet Audit — red/blue team audit — 2026-08-24

**Auditor:** ICJIA development team (with Claude Code)
**Baseline:** 2026-06-06 audit (v1.21.x — `/sites` roster + OG pipeline + CSP).
**Scope of this review:** the **live product only** — the Node pipeline (scan →
references/sitemap → og-meta → audits → introspect) and the deployed web-rollup
bundle. The MCP server (`src/mcp/*`) and npm/CLI-distribution paths are
**deprecated/unused** and were treated as dead surface (one posture fix applied
anyway, FC-2026-037).
**Result:** 1 real bug (Medium — fixed), 1 defence-in-depth posture fix
(fixed), 4 tracked Low residuals. 0 exploitable XSS. 0 credential leaks. Tests
**1715/1715** green at close; lint clean.

## Method

Four parallel deep-dives plus first-hand review: (1) XSS trace across every
HTML generator, (2) office/PDF parser configuration (XXE / zip-slip / pdfjs),
(3) network / SSRF / credential handling, (4) shell / path-traversal. Each
untrusted-data path (content scraped from the 12 fleet sites — filenames, URLs,
page titles, OG metadata, Strapi fields, sitemaps) was traced from source to
sink.

## Findings

### FC-2026-036 — Medium — FIXED in v1.63.0

**Server-side SSRF via scraped URLs with no host/IP allowlist.**

*Threat.* Two build-time fetches took a URL whose host+scheme came from content
served by an audited (untrusted) site:

- `src/references/sitemap.js` — `fetchSitemapUrls()` recursively `fetch()`ed
  every sub-sitemap `<loc>` parsed out of the fetched XML body, with no
  validation.
- `src/references/og-meta.js` — `fetchOgMeta()` / `fetchImageBytes()` fetched
  the scraped `og:image` / page URL (http(s)-only, but no host/IP guard).

A malicious or compromised fleet site returns a `<sitemapindex>` (or `og:image`)
pointing at `http://169.254.169.254/latest/meta-data/…` (cloud metadata),
`http://127.0.0.1:6379/` (a local service), or a private-LAN address, and the
run fetches it. Blind SSRF (sitemap responses are only re-parsed as XML; image
bytes are only embedded when < 5 MB and a whitelisted type) and no credential is
attached — but the reach is real, and worse in the CI/cron mode the tooling
supports, where cloud-metadata credential theft becomes possible. Node's global
`fetch` also follows redirects by default, so an initial-host allowlist alone
would be bypassable via a 302.

*Fix.* New `src/util/safe-fetch.js`:
- `isBlockedAddress` / `isBlockedHost` reject loopback (`127.0.0.0/8`, `::1`),
  unspecified (`0.0.0.0`, `::`), link-local incl. metadata (`169.254.0.0/16`),
  RFC1918 (`10/8`, `172.16/12`, `192.168/16`), CGNAT (`100.64/10`), IPv6 ULA
  (`fc00::/7`) and link-local (`fe80::/10`), IPv4-mapped forms, and
  `localhost` / `*.local` names.
- `safeFetch()` validates the host, then fetches with `redirect: "manual"` — the
  only request it issues goes to the validated host, and a redirect is never
  chased into a private address.

Both fetch sites route through `safeFetch`. Covered by `test/safe-fetch.test.js`
plus SSRF cases in `test/references-sitemap.test.js` and `test/og-meta.test.js`.

*Residual (accepted).* A hostname that *resolves* to a private address
(split-horizon DNS / DNS rebinding) is not caught — that needs connection-time
IP pinning, disproportionate for a best-effort build-time tool on the operator's
workstation. The literal-IP, localhost, and redirect vectors — the demonstrated
exploit — are closed.

### FC-2026-037 — Low (posture) — FIXED in v1.63.0

**MCP server exposed the whole filesystem by default.**

`src/mcp/tools.js` treated an unset `FILECAP_MCP_ALLOWED_PATHS` as "no
restriction" — whole-filesystem read (scan/query) + arbitrary-path write
(report/web-rollup). Now **default-deny**: access is confined to the default
audits base (`~/filecap-audits`) unless an allowlist is set explicitly; the
startup notice was updated from "UNRESTRICTED" to "restricted to the default
base". The MCP server is deprecated/unused, so this is posture only, but the
default is corrected regardless. Covered by `test/mcp-tools.test.js`.

## Tracked residuals (open — defence-in-depth, low severity)

- **FC-2026-038 — credentialed fetchers rely implicitly on undici stripping
  `Authorization` across cross-origin redirects.** `auth-fetcher.js` /
  `score-fetcher.js` / `page-scorer.js` use default `redirect:"follow"` with no
  explicit same-host guard. Safe on Node ≥ 20 (undici strips sensitive headers
  cross-origin) but fragile if the fetch impl is ever swapped. *Recommend:*
  `redirect:"manual"` + re-attach only on same host.
- **FC-2026-039 — `bearerLogin` refresh forwards the cleartext password on a
  307/308 redirect.** undici strips headers on redirect but not the request
  body; a compromised *configured* auth host could 307 the login POST to an
  attacker origin. *Recommend:* `redirect:"manual"` on the login POST.
- **FC-2026-040 — `gitRepo` reaches `git clone` with no scheme validation**
  (`src/references/git-repo.js`). `execFileSync` uses no shell, but a git URL is
  itself an exec vector (`ext::sh -c …`) and a leading `-` is option injection.
  Trusted-roster today. *Recommend:* validate against
  `^https://github\.com/[\w.-]+/[\w.-]+(\.git)?$` and reject leading `-`.
- **FC-2026-041 — `score` interpolated into HTML without a local escape**
  (`src/report/site-accessibility-section.js`). Safe only by an upstream numeric
  coercion in `aggregate.js`. *Recommend:* a defensive numeric cast / `esc()` to
  match the surrounding code.

## Confirmed clean (no finding)

- **No exploitable XSS** anywhere. Centralized `escapeHtml` + a `safeUrl()`
  scheme gate on every `href`; scraped data only contributes the *path* of a
  trusted-base URL, so `javascript:` can't be injected even under the CSP's
  `script-src 'unsafe-inline'`. The search page renders via
  `createElement`/`textContent` (never `innerHTML`); the search index is a
  standalone JSON file, not embedded in a script; `og:title` is decoded then
  discarded, `og:description` re-escaped at render.
- **Parsers hardened against malicious documents.** pdfjs runs with
  `isEvalSupported:false` and no scripting; fast-xml-parser does not resolve
  external entities (**no XXE**); all zip access is in-memory (**no zip-slip**).
- **CSV formula-injection guard** — `csvCell` prefixes leading `= + - @` and
  doubles quotes (reused by the new error-log CSV).
- **Credential hygiene** — tokens/passwords live in mode-0600
  `~/.filecap/secrets.json`, written atomically, never logged, never in deployed
  output, and only attached to config-derived hosts. No TLS bypass anywhere.
- **Shell layer** — remote paths shell-quoted with `printf '%q'`; untrusted
  remote filenames are rsync'd as data and read via `fs` (never a shell);
  symlinks skipped on walk.
- **Access control** — the whole bundle sits behind a server-side Netlify Site
  Password (401); the client-side gate is defence-in-depth. Origin IPs / server
  paths remain stripped from output (FC-2026-033).

## New — logging (v1.63.0)

`src/util/logger.js` adds structured, **redacted** error records; `filecap
audits` writes a per-run `errors-<runId>.ndjson` + `.csv` under
`~/filecap-audits/_runs/` for debugging and for managers/auditors. These are
**local only, never in the deployed bundle** — deliberately, so verbose error
context cannot reintroduce the origin-infrastructure exposure FC-2026-033
removed. `logs.sh` reads them locally.
