## Findings

### FC-2026-018 — Moderate — FIXED in 1.6.6

**`audit-static.sh` exposed `FILECAP_GITHUB_TOKEN` in `ps aux` argv.**

When the auditor used the `FILECAP_GITHUB_TOKEN` env-var path (the fallback when `gh auth login` isn't available), `audit-static.sh` built an authenticated URL of the form `https://x-access-token:<TOKEN>@github.com/<owner>/<repo>.git` and passed it as a positional argument to `git clone` / `git remote set-url`. On macOS and Linux, process arguments are world-readable: any other local user could run `ps aux | grep git` during the ~10-second clone window and read the token.

Impact: low on a single-user audit-lead machine (the typical environment); higher on shared workstations. Token scope is `repo` (read-only with default `gh` flow), and tokens are user-rotatable, so the blast radius is small. The `gh CLI` auth path (preferred and documented) was never affected — gh's credential helper handles the auth without ever putting a token in argv.

**Fix (1.6.6):** `audit-static.sh` now passes the PAT via the `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_0=http.extraheader` / `GIT_CONFIG_VALUE_0=...` env-var triple instead of inlining the token into the URL. The clone/fetch URL is always the clean `https://github.com/<owner>/<repo>.git`. Process environment is readable only by the same UID on macOS/Linux (unlike argv, which is world-readable), so the token is no longer visible to other local users. A `git_with_auth` helper function wraps every git invocation; the gh CLI path is unchanged. Pre-existing `.git/config` entries with token-bearing URLs (from earlier runs of the buggy script) are scrubbed on the first new run.

### FC-2026-019 — Note — Accepted

**Master CSV + duplicates CSV in the deployed bundle increase data-exposure surface.**

`audit-file-list-master.csv` (~16 MB for the current 16-site fleet) and `audit-file-duplicates.csv` (~300 KB) join the per-site CSVs in the bundle. A successful unauthenticated download of either reveals the full file path of every audited document on every server. This is *not new* — per-site CSVs already had the same shape — but the master CSV concentrates everything into a single artifact.

**Mitigation:** the production deployment uses Netlify Pro Site Password, which gates every file in the bundle (verified HTTP 401 on `/audit-file-list-master.csv`, `/audit-file-duplicates.csv`, and per-site CSVs in the 1.5.6 deployment review). `robots.txt` + `X-Robots-Tag: noindex, nofollow` cover the search-engine angle. Accepted as documented residual risk; no code change.

### FC-2026-020 — Note — Accepted

**`~/.filecap/secrets.json` has a well-known path; any same-UID process can read it.**

File mode is enforced at `0600`, so other users on the machine cannot read it. But any process running as the audit lead's own UID can — including arbitrary npm packages installed by them, browser extensions with file-system access, malware-as-user, etc. The trust boundary is the user account itself, the same way `~/.ssh/id_ed25519` works.

**Mitigation:** the env-var override (`FILECAP_BEARER_TOKEN_<SERVER>`) supports the workflow where a user prefers their token never live on disk — typically via `op run --` (1Password CLI) injecting at invocation time. Documented in README's "Sites that require a bearer token" section. Accepted as the standard user-account trust model; no code change.

### FC-2026-021 — Note — Accepted

**`audit-static.sh` clones into `~/filecap-audits/<name>/clone/` — same user-account trust boundary as the Strapi mirrors.**

The cloned repo contents include whatever's in the GitHub source — code, config files, sometimes `.env.example` placeholders, README, etc. A malicious repo could include files designed to exploit pdfjs/jszip parsing (already documented as FC-2026-012 / FC-2026-013). The clone dir is mode 700 (verified).

**Mitigation:** same as the Strapi mirror dirs. The auditor is expected to clone only repos they trust. The `gh auth login` path means the auditor is already authenticated to GitHub with their own credentials and is voluntarily cloning each repo (one-time addition to sites.json). No change.

### FC-2026-022 — Note — Reviewed

**New inline JavaScript in the per-site HTML report** (added in 1.4.0 + 1.5.7 + 1.5.8 + 1.6.5: pointer-events pan, sticky back-link, CSV download link, image-only filter chip).

Reviewed all new JS for the XSS surface that FC-2026-008's regression suite covers (server-name, site-name, hostname, filename, path). All new handlers use class-list manipulation (`classList.add` / `classList.remove`), DOM attribute reads (`dataset.filter`), and element queries (`querySelectorAll`). **No `innerHTML`, no `eval`, no `Function()`, no template-string interpolation of user data into DOM.** The pointer event handlers operate on the wrapper's `scrollLeft` only. The image-only filter compares `row.classList.contains("image-only")` against a value set at render time from the validated inventory data.

Verified no new XSS vector; no change needed.
